# ADVERSE JUDGE 0.4.0 — рабочая студия рекламных обещаний

**Статус: готовый к локальному пилоту и закрытому staging исходный проект. НЕ production и НЕ опубликован на семи рекламных сайтах.**

JUDGE — не декоративный чат. Это state-machine: рекламное обещание → позиция обвинения → выбор ограниченного действия → ввод фактов о продукте → три варианта → решение автора → версионированный бриф → передача → проверяемое внешнее событие. Все изменения дела определяются кодом и журналом событий; LLM при разрешении пользователя даёт только комментарии, не меняет дело.

## Запуск за минуту

Нужен **Node.js >=22.13.0**, проверен на Node 22.16.0. Приложение не использует npm-зависимостей.

```bash
npm start
```

В браузере откройте **http://localhost:3000**. Для Windows есть `START_WINDOWS.cmd`; для macOS/Linux `sh start.sh`. Не запускайте две версии на одной базе одновременно.

Без Node можно открыть `dist/JUDGE-ADVERSE-preview.html`. В автономной версии доступны три ветки, вердикт, экспорт и ручной бриф; аккаунты и реальные свидетели работают **только в серверной версии**, и она по умолчанию не вызывает внешние API.

## Главное в v0.4.0

- **Управление сеансами в интерфейсе.** Просмотр устройств (только грубая классификация), завершение других или текущего сеанса. Только для зарегистрированного аккаунта. Время последнего посещения обновляется сервером.
- **Смена пароля** с проверкой старого и новым HttpOnly cookie + CSRF; все старые сеансы пользователя становятся недействительными. Локальная защита от подбора пароля теперь также записывает счётчик неуспешных входов в SQLite, поэтому перезапуск сервера не снимает кратковременную блокировку.
- **Безопасный повтор интеграции.** Принимающий сайт может повторить `redeem` с тем же сохранённым `requestId`, если потерял ответ, в течение 5 минут; второй `handoff_redeemed` не создаётся. Другой ключ повтор не разрешает.
- **Server-only SDK для внешних платформ** `integrations/receiver-sdk.mjs`; запрещает автоматические HTTP redirects и обычный HTTP на публичном домене, обрабатывает ошибки и требует устойчивые идентификаторы.
- **Операторские утилиты:** `npm run ops:doctor`, `npm run backup:inspect -- path/to/backup.sqlite`, `GET /api/ready`; проверка целостности базы и независимая репетиция восстановления.
- **План закрытого staging:** конфигурация Docker/Caddy + Basic Auth, техническая документация и отдельная RFC миграции в Postgres/Supabase. Docker/Caddy в среде сборки не испытывались.
- **Миграция SQLite v2→v3** без удаления состояний и журнала (см. ниже).

## Проверки

```bash
npm run check                 # синтаксис модулей
npm test                      # сервер, domain, API, auth, интеграции, upgrade, backup
npm run demo                  # пересобрать автономное HTML-превью
npm run verify                # integrity + replay рабочей SQLite
npm run integrations:check    # причины отсутствия готовности A–G
npm run ops:doctor            # эксплуатационные предупреждения без значений секретов
npm run backup                # snapshot SQLite + SHA-256 и replay
npm run backup:inspect -- /path/to/JUDGE-backup.sqlite
```

Проверенная среда: Node 22.16.0 и Chromium. Отчёт QA в `reports/TEST-REPORT-v04.md`. В отчёте раздельно отмечены автоматические и браузерные проверки, ограничение HTTP bridge, отключённый реальный ИИ и отсутствие живых A–G.

## Где хранятся данные

По умолчанию — `data/judge.sqlite`, не в `public/`. Сервер использует WAL, иностранные ключи, транзакции, DB replay и ограничения прав файла. Сессии — HttpOnly SameSite=Strict cookie. После отключения аккаунта на устройстве соответствующий токен больше не подходит. Доступ к делам проверяется по owner ID.

`npm run backup` создаёт **нешифрованную** резервную копию и JSON с SHA-256. Храните их в зашифрованном внешнем хранилище. Удаление активных данных **не удаляет** имеющиеся у оператора старые резервные копии.

## Обновление с 0.3.0

1. Остановить JUDGE 0.3.0 (`Ctrl+C` / SIGTERM). Сделать независимую резервную копию SQLite и проверить её.
2. Распаковать 0.4.0 **отдельно** от прежней папки. Перенести базу `data/judge.sqlite` из остановленного приложения в новую папку или указать `JUDGE_DB`.
3. `npm start` автоматически переведёт `PRAGMA user_version=2` в `3`: добавятся поля сеансов, хэш запроса для безопасного повторного redeem и счётчики неверных логинов. События дел останутся прежними.
4. Проверить `npm run verify` и открыть старое дело.
5. Для отката на 0.3.0 нужна заранее сохранённая копия БД версии 2; старый сервер на v3 запускать нельзя.

## Реальная интеграция с семью сайтами

A–G присутствуют как явные **неподключённые** конфигурации. Ручной экспорт брифа есть, но это не доставка и не рекламная конверсия. Передавать бриф можно только по подтверждённому контракту — на сервере каждого конкретного сайта с отдельной авторизацией. См. `docs/RECEIVER-INTEGRATION-RU.md`, `docs/INTEGRATION-CONTRACT-RU.md`, `docs/API.md`.

Внешний ИИ отключён. Для подключения требуется собственный ключ, конфигурация модели и отдельно подтверждённая передача содержания дела. Не помещайте секреты в Git или клиентские файлы.

## Почему ещё нельзя открывать всему интернету

Встроенный аккаунт **не подтверждает адрес email**, не имеет восстановления пароля и MFA; нет общей идентификации пользователей семи сайтов, облачного PostgreSQL runtime, живых интеграций и операционных процессов GDPR. Для публичного релиза нужен проверенный IdP/SSO, продуманная миграция SQLite в БД для нескольких экземпляров, политика хранения, эксплуатационный мониторинг и live E2E партнёров. Конфигурация `deploy/` рассчитана только на **закрытый staging за Basic Auth**.
