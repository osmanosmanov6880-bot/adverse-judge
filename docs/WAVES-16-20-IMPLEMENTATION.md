# ADVERSE JUDGE v0.25.0 — Waves 16–20. Техническое описание

Релиз 22.10.2026. Основание — рабочий исходный код v0.20.0. Вся функциональность ниже реализована в сервере, SQLite и браузерном UI. Это **локальный пилот**, а не публичный SaaS или подтверждённое подключение семи сайтов.

## Полный маршрут

`JUDGE case → versioned brief → campaign → independent human evidence review → creatives → issue resolution → declared budget → independent editorial approval → immutable release → controlled partner handoff → internal audit`.

Все действия защищены серверной проверкой полномочий; действия над кампанией используют `expectedRevision` для отклонения устаревшего интерфейса. Результаты ручного ввода не выдаются за провайдерскую телеметрию.

## WAVE 16 — Creative ↔ Evidence Traceability

**Где:** `server/governance.mjs` (`policy`, `bind`, `unbind`, `validEvidence`, `gate`), `public/governance.mjs`, `server/production.mjs` (preflight). **Схема:** `campaign_evidence_policy`, `campaign_claim_links`.

Владелец может включить обязательное связывание каждого рекламного варианта с хотя бы одним действительным источником. Источник должен относиться к той же кампании и тому же брифу, быть отмеченным *другим* уполномоченным редактором и не быть просроченным. Уход проверяющего из команды делает такую проверку недействующей; редакторское согласование пересчитывается на актуальном состоянии. Включение политики, добавление и снятие связей увеличивают редакцию кампании и инвалидируют прежние одобрения. **Ограничение:** редакторское «изучено» не подтверждает подлинность документа.

## WAVE 17 — Risk / Issue Register

**Где:** `governance.issueCreate/issueResolve`; **схема:** `campaign_issues`.

У кампании есть критические, серьёзные и малые замечания. Критическое замечание блокирует новое согласование и выпуск; его автор не может его закрыть — требуется другой участник с правами редактора и содержательное обоснование. Повторное закрытие, доступ к чужим замечаниям и попытки использовать устаревшую редакцию отклоняются. После удаления аккаунта его прежние независимые закрытия переходят в открытое состояние.

## WAVE 18 — Declared Budget Governance

**Где:** `governance.budget/spending/gate`; **схема:** `campaign_budgets`; ранее существующие `campaign_observations`.

Владелец устанавливает валюту (EUR/USD/SEK/GBP), порог в минимальных денежных единицах и поведение `warn`/`hold`. Суммируются только неотозванные записи ручного расхода в той же валюте. Режим `hold` блокирует новый выпуск при превышении, а `warn` показывает предупреждение. Это **не реальные лимиты в рекламном кабинете**: сайт-партнёр не получает никаких команд на остановку расходов, а значения введены пользователем вручную.

## WAVE 19 — Workspace Emergency Stop

**Где:** `governance.controlUpdate/assertDispatchAllowed`, `server/advanced.mjs`; **схема:** `workspace_controls`, `workspace_operational_events`.

Владелец рабочего пространства задаёт причину и включает аварийный стоп внешних передач. Сервер прекращает выдачу новых токенов и использование ещё не предъявленных токенов, отзывает все `issued` внутри пространства. После возобновления отозванные токены **не восстанавливаются**. Уже предъявленные партнёром объекты и подтверждения не меняются задним числом. Это не дистанционное удаление рекламы и не остановка уже работающих кампаний партнёра.

## WAVE 20 — Workspace Portfolio & Verifiable Internal Audit

**Где:** `governance.portfolio/exportAudit`, `scripts/verify-governance.mjs`, `public/governance.mjs`.

Участник команды видит доступные ему кампании и их фактические блокеры; редактор может скачать JSON-аудит конкретной кампании (версии, ссылки на источники, замечания, лимит, решения, отпечатки выпусков, ручные наблюдения). Скрипт:

```bash
npm run audit:verify -- exported-audit.json
```

повторно считает SHA-256 по сериализованному payload. Это обнаруживает изменение **без замены контрольной суммы**; SHA-256 не удостоверяет автора, не является цифровой подписью и не подтверждает соответствие требованиям закона.

## HTTP API — все эндпоинты требуют входа и корректного Origin/CSRF

| Метод | Маршрут | Назначение |
|---|---|---|
| GET | `/api/governance/campaigns/:id` | Текущее состояние пяти блоков |
| POST | `/api/governance/campaigns/:id/policy` | Политика обязательных источников |
| POST | `/api/governance/campaigns/:id/link` | Привязка `creativeId + evidenceId` |
| POST | `/api/governance/campaigns/:id/unlink` | Удаление связи |
| POST | `/api/governance/campaigns/:id/issue` | Замечание `severity, title, details` |
| POST | `/api/governance/campaigns/:id/issue-resolve` | `issueId, note` |
| POST | `/api/governance/campaigns/:id/budget` | `currency, capMinor, mode` |
| GET | `/api/governance/campaigns/:id/audit-bundle` | JSON-аудит |
| GET | `/api/governance/workspaces/:id/portfolio` | Актуальное портфолио |
| POST | `/api/governance/workspaces/:id/control` | Стоп / возобновление, `reason` |

Мутации, изменяющие кампанию, требуют `expectedRevision`, кроме переключателя стопа пространства. Ошибки прав, конкурирующих версий, неизвестного состояния и чужих объектов возвращаются структурированным HTTP-ответом; UI не выполняет локального обхода блокеров.

## Миграция и хранение

SQLite `PRAGMA user_version=17` → `22`: добавлены таблицы контроля доказательств, замечаний, бюджета, паузы и журнала операций пространства. Старые дела, голоса, кампании, выпуски и события не перезаписываются. Обновление **не включает строгую политику источников для старых кампаний автоматически**. Откат на старый бинарник требует резервной копии старой схемы.

## Реальные ограничения и production gates

- A–G: **0/7** настоящих интеграций; только тестовый принимающий HTTP-сервис. Не маркировать mock как производственную доставку.
- Локальная SQLite и локальные аккаунты; ещё нет проверенного email/SSO/MFA и Postgres; нельзя объявлять масштабируемый multi-tenant SaaS.
- Нет доказанного легального clearance, судебной проверки рекламы, подтверждённых показателей эффективности и подключённых автоматических расходных лимитов.
- Ссылки/события в журнале отражают решения пользователей; журнал с HMAC требует отдельного защищённого секрета до создания базы.
- Публичное развёртывание требует внешнего penetration test, антифрода, мониторинга, восстановления резервной копии на независимом узле и договоров обработки данных.
