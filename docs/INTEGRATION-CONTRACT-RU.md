# ADVERSE JUDGE 0.3 — контракт подключения платформ A–G

## Что есть и чего пока нет

- Есть серверная подписанная передача **конкретной версии вердикта**, однократный redeem, возможность отзыва до получения, запрет устаревших версий и аутентифицированные подтверждения событий.
- Режим `clipboard` не отправляет данные на сайты и **никогда не считается доставкой**. `mode:api` намеренно возвращает `NOT_CONFIGURED`: для настоящего API нужны документы целевого сайта и отдельный адаптер.
- `deeplink` становится доступен только после `verified:true`, валидного публичного HTTPS URL, `credentialEnv` с секретом ≥20 символов и `HANDOFF_SECRET` ≥32 символов. Статус «contract_ready_not_live_verified» означает конфигурацию, **не пройденное live E2E испытание**.
- В исходном наборе **все A–G остаются не подключены**, потому что нет их реальных URL/API. Не подставляйте произвольные URL.

## Схема config/platforms.json

```json
{
  "id": "A",
  "name": "Название подтверждённой платформы",
  "mode": "deeplink",
  "verified": true,
  "url": "https://your-verified-partner.example.com/judge-import",
  "credentialEnv": "PLATFORM_A_CREDENTIAL",
  "confirmedEvents": ["ad_created", "ad_exported"]
}
```

Это **пример одной записи**; `config/platforms.json` — массив. Сначала получите контракт и подтвердите владение доменом и согласование авторизации. Не меняйте `verified` до реального технического согласования. Не раскрывайте переменные `PLATFORM_*_CREDENTIAL` или `HANDOFF_SECRET` в клиенте, Git, скриншоте или сообщении. Секреты серверов JUDGE и принимающего сайта должны храниться и ротироваться отдельно. Для отдельного манифеста используйте `JUDGE_PLATFORMS_FILE=/path/to/platforms.json`.

`npm run integrations:check` проверяет локальную конфигурацию и выдаёт причины отсутствия готовности без значений секретов. `npm run integrations:strict` завершится ошибкой, пока все семь не настроены. Эти проверки НЕ делают внешних запросов и не подтверждают, что сайт действительно работает.

## Протокол передачи

1. Пользователь завершает дело, выбирает платформу и отдельно подтверждает передачу.
2. JUDGE создаёт версионированную запись `handoffs` с snapshot брифа и одночасовым сроком; в URL добавляется подписанный параметр `judge_token`, содержащий только ID, platform ID, expiration и версию протокола, **не сам бриф**.
3. Принимающий сайт получает параметр и **только со своего сервера** вызывает `POST https://judge.example.com/api/integrations/redeem` с заголовком `Authorization: Bearer <PLATFORM_A_CREDENTIAL>` и JSON:

```json
{"platformId":"A","token":"<signed judge_token>"}
```

4. JUDGE проверяет подпись, срок, статус отзыва, ownership оригинального дела, актуальность версии вердикта, совпадение платформы и однократность. Только после этого возвращает `{ "handoffId": "...", "brief": { ... } }` и отмечает `handoff_redeemed`.
5. **Действие создано** только когда целевая платформа действительно его совершила и отправила с сервера `POST /api/integrations/events` с тем же bearer:

```json
{"platformId":"A","handoffId":"<UUID>","eventId":"external-ad-event-001","action":"ad_created"}
```

6. Ответ `{ "ok":true, "duplicate":false }` создаёт `useful_action`; идентичный повтор возвращает `duplicate:true`. Повтор `eventId` для другого handoff/action даёт `EVENT_CONFLICT`. `action` должна входить в allowlist `confirmedEvents` этого партнёра.

## Отзыв и повторное редактирование

До redeem автор может вызвать `POST /api/cases/{id}/handoff-revoke` с обычными cookie + CSRF + `commandId` + `expectedVersion` + `handoffId`. Отзыв пишется в журнал. После redeem JUDGE не обещает «стереть» переданную копию: управлять ею обязан принимающий сайт. При `owner_reopen`, новом `verdict_issued` или `witness_objection` все ещё не полученные signed handoffs для данного дела автоматически отзываются. Ручной clipboard экспорт отменить невозможно.

Ранее созданные в 0.2.0 unredeemed handoffs имеют `verdict_id=null` после миграции; они **не могут быть погашены** из-за отсутствия доказательства версии. Создайте новую передачу после upgrade.

## Требования к принимающей платформе

- HTTPS/HSTS, защита токена от рефереров и сторонних скриптов, отсутствие логирования токена в URL, одноразовая обработка входа.
- Никакого вызова JUDGE bearer API из браузера. Возвращённый бриф хранить согласно политике данных организации.
- Серверное подтверждение `ad_created` только после фактического создания объявления, а не клика, перехода или просмотра.
- Устойчивость к HTTP 401/403/409/410/429/5xx; retry только безопасных запросов с сохранением external event ID.
- Отдельный согласованный срок хранения импортированных данных, удаление и аудит доступа.

## Базовые проверяемые кейсы

- Подлинный signed token принимается один раз; повтор — `REDEEMED`.
- Подмена подписи/платформы/просрочка/отзыв/устаревший вердикт — отказ без брифа.
- Неверный bearer — 401 без раскрытия сведений.
- Только allowlisted event, повтор same-ID/same-payload — безопасен; same-ID/different-payload — конфликт.
- Отказ/таймаут партнёра не рисует событие `useful_action`.
- Смена вердикта не переносит прежнее согласие пользователя на новую передачу.

До публикации обязательно провести live E2E на staging каждого конкретного сайта: локальная проверка контракта не заменяет реального соединения.

## Расширение v0.4 — recoverable redeem

Если ответ HTTP потерялся после того, как JUDGE выдал бриф, принимающий backend вправе повторить **строго тот же** `requestId` в ближайшие 5 минут, пока signed token действителен и версия вердикта актуальна:

```json
{
  "platformId": "A",
  "token": "<signed judge_token>",
  "requestId": "persisted-receiver-request-001"
}
```

Первый успешный ответ: `{ "handoffId":"...", "brief":{}, "duplicate":false }`; идентичный повтор: `duplicate:true` с тем же брифом. **Без** `requestId` сохраняется строгая однократность v0.3. Передавать новый `requestId` при retry запрещено, иначе 409. Целевой сайт обязан хранить request ID в собственной БД до вызова.

Эта особенность не превращает тестовую интеграцию в подтверждённое `useful_action`. SDK `integrations/receiver-sdk.mjs` — образец для server-to-server; внешние платформы требуют своего API контракта и E2E на staging.
