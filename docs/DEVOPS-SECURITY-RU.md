# Эксплуатация и безопасность ADVERSE JUDGE 0.10.0

## Настройка

- Используйте Node.js >=22.13 с обновлениями безопасности. Публичный сервер без отдельного входного шлюза **не поддерживается**.
- Для локального тестирования достаточно `npm start` и `http://localhost:3000`.
- Для закрытого HTTPS staging: APP_ORIGIN должен совпадать с внешним доменом, настройте TLS и ограничение доступа **до** открытия сервиса. Просмотрите `deploy/` и `docs/STAGING-OPERATIONS-RU.md`; наличие файла compose не означает настроенного безопасного сервера.
- Секреты `HANDOFF_SECRET`, `JUDGE_LEDGER_SECRET`, `OPENAI_API_KEY`, `PLATFORM_X_CREDENTIAL` всегда только в защищённой конфигурации backend, не в JS браузера и не в архиве.
- Длительные ключи HMAC требуют управления жизненным циклом. Изменение существующего ledger key отклоняется, нет автоматической ротации.

## База / аудит

`npm run verify` — read-only проверка SQLite, иностранных ключей, воспроизводимости бизнес-состояния из событий и подписи цепочки. Для другого пути установите `JUDGE_DB` либо передайте аргумент CLI `node scripts/verify-db.mjs /path/to/judge.sqlite`.

`npm run backup` создаёт локальный backup и digest; `npm run backup:inspect` проверяет локальный snapshot. **Эти команды не настраивают зашифрованную offsite-репликацию или автоматическое восстановление.** Оператор обязан внедрить расписание, объектное хранилище и регулярные тесты восстановления.

`npm run ops:retention` — dry-run. `npm run ops:retention:apply` — необратимо удаляет просроченные неиспользованные ссылки/сеансы и требует регламента. Обе команды не удаляют голоса и историю дел. Это техническая уборка ссылок, не полный GDPR retention schedule.

## Реальные границы безопасности

- На HTTP: проверка Origin/CSRF, SameSite + HttpOnly cookie, ограничение загрузки JSON и лимиты, контентный CSP, защита от доступа к произвольным файлам, подписи интеграций.
- На уровне данных: кейсы привязаны к владельцу, участникам workspace доступно только явно опубликованное дело, передача рекламы отделена от её фактического создания.
- SQLite не предоставляет RLS Postgres; защита обеспечивается проверками в серверном коде. Регрессии этих проверок опасны; включён unit/browser QA.
- Нет email verification, MFA, управления корпоративной идентичностью и подтверждённых производственных SLA; это **блокеры внешнего public deployment**.
- Один одноразовый токен Evidence Room ≠ один реальный человек; полноценная защита от мультиаккаунтов и ботов отсутствует.
- Статистический Wilson 95% для добровольного опроса не означает representativeness или причинную оценку рекламной эффективности.
- Нет настройки согласия на cookies внешней аналитики, не проведён юридический data protection impact assessment или независимый pen-test. До международной продажи требуется полноценная оценка применимого законодательства.

## Диагностика

`npm run ops:doctor` проверяет часть локальных настроек, но не может доказать публичный TLS, offsite backup, договоры с процессорами, SSO, anti-fraud или реальный доступ к рекламным платформам.

`npm run integrations:audit` читает манифест A–G; в этом релизе честный результат **0/7**. `npm run integrations:conformance` использует синтетический loopback HTTP, а не публичные сайты пользователя.

## Политика при сбое

1. Остановить запись и **не отключать** проверку журнала, чтобы «починить» блокировку.
2. Сделать backup битого состояния без подмены старой хорошей копии.
3. Проверить `npm run verify` с правильным HMAC-ключом.
4. При повреждении — восстановить последнюю прошедшую проверку резервную копию, затем сверить доменные события.
5. Если публичные данные затронуты — по процедуре incident response, с оценкой обязанностей уведомления и безопасной ротацией затронутых ключей/сеансов.
