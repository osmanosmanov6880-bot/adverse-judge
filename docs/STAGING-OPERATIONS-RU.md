# ADVERSE JUDGE v0.4 — закрытый staging, операции и ограничения

## Что это

Работающий Node/SQLite пилот с новой защитой сеансов, интеграционным контрактом, диагностикой и проверяемым резервным копированием. **Не публичный SaaS и не подтверждение production readiness.** Email не подтверждается; нет сброса пароля, MFA, централизованного SSO, облачного хранилища, политики резервных копий вне сервера, юридического аудита и проверенных A–G.

## Локальный запуск

1. `node -v` — нужен >=22.13; установка зависимостей не нужна.
2. `npm start` — на `http://localhost:3000`. Если порт занят: скорректировать `PORT` и `APP_ORIGIN` согласованно.
3. `npm run check`, `npm test`, `npm run ops:doctor`, `npm run integrations:check`.
4. `npm run backup` после создания хотя бы одного дела. Результат — `.sqlite` и `.sqlite.json` с SHA-256.
5. `npm run backup:inspect -- backups/<имя>.sqlite` повторяет проверку на копии, не затрагивая рабочую базу.

## Неразрушающее обновление с v0.3

- Остановить старый сервер. Сделать независимую и проверенную резервную копию текущей базы (`npm run backup` + `npm run backup:inspect`). Не запускать две версии на одной SQLite базе.
- Распаковать v0.4 **в другую папку**. Перенести исходный файл базы из папки `data` (на остановленном сервере) и её настройки доступа.
- Старт v0.4 мигрирует `user_version 2 → 3`, добавляя хэш idempotent-redeem, метаданные сеансов и счётчик неудачных входов. Предыдущие дела и журнал сохраняются.
- После миграции `npm run verify`, `npm test`. Откатить бинарник без отката базы нельзя: для v0.3 нужна предварительная независимая копия SQLite v2.

## Частный staging с TLS (не production)

Файлы `deploy/Dockerfile`, `deploy/compose.staging.yaml` и `deploy/Caddyfile.staging` — конфигурация для закрытого staging. Требуются Docker Compose, DNS, внешний доступ 80/443 для Caddy TLS и операторские секреты. **В текущей среде Docker недоступен; запуск контейнера и сертификаты не испытаны.**

- Создайте `.env.staging` по `deploy/env.staging.example` (не коммитьте). Укажите реальный `JUDGE_DOMAIN`, пользователя и bcrypt-хэш для HTTP basic auth (Caddy hash-password), отдельные серверные секреты при наличии подтверждённых интеграций.
- Из каталога проекта: `docker compose --env-file .env.staging -f deploy/compose.staging.yaml config` — сначала проверьте конфигурацию. Затем `docker compose --env-file .env.staging -f deploy/compose.staging.yaml up -d --build`.
- Внешний порт Node.js не опубликован. Caddy защищает **все** маршруты basic auth, включая одноразовые ссылки свидетелей. Для тестов с пользователями им необходимо предоставить доступ к staging.
- `docker compose --env-file .env.staging -f deploy/compose.staging.yaml ps`, просмотр редактированных логов и `/api/ready` за приватным паролем.
- Резервные копии тома SQLite нужно организовать отдельно; Docker named volume **не заменяет** offsite backup.

## Безопасность

- Не публикуйте `data/`, `.env`, `backups/`, ключи API и partner credentials. Следите за доступом к файлам БД и резервным копиям.
- Публичный аккаунт на email без подтверждения почты можно захватить до регистрации владельца адреса. Поэтому staging закрыт; для публичного релиза требуется верифицированная авторизация.
- Ошибочные пароли блокируются на уровне IP и хэша email в SQLite. После смены пароля все прежние сеансы закрываются, а текущий токен и CSRF ротируются.
- Срок подтверждения передачи 1 час; повтор получения по тому же `requestId` допускается максимум 5 минут при неизменном вердикте. Внешняя платформа не может подтвердить неподдерживаемое действие.
- Защита GDPR и соответствие другим законам не заявлены. Нужны DPA, политика хранения, доступ/удаление, верификация личности, инцидентный процесс и тестирование в отдельном окружении.

## Честные ограничения готовности

`npm run ops:doctor` **всегда** указывает `productionReady: false`, даже при успешных локальных тестах. Это не ошибка: приложение остаётся закрытым пилотом, пока не завершены проверенная авторизация, многопользовательская инфраструктура, независимый pentest, real API A–G и эксплуатация с мониторингом.
