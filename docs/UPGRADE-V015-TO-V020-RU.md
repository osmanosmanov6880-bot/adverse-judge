# Безопасное обновление ADVERSE JUDGE 0.15.0 → 0.20.0

Только для приватного локального пилота. SQLite обновляется автоматически при первом запуске новой версии. Схема меняется **12 → 17**, обратного автоматического преобразования нет.

1. Остановите старый процесс JUDGE. Не запускайте два процесса с одним файлом базы.
2. Используйте штатную команду `npm run backup` прежнего релиза или сделайте согласованную SQLite backup-копию. Не копируйте одну только `.sqlite` во время активной записи: SQLite может использовать файлы WAL.
3. Сохраните серверные значения `JUDGE_LEDGER_SECRET`, `HANDOFF_SECRET`, `APP_ORIGIN` и конфигурацию партнёров отдельно от архива. При смене ключа журнала проверка может перестать работать.
4. Распакуйте 0.20.0 в **новую папку**. Не кладите новую копию поверх старого каталога с рабочими данными.
5. Укажите `JUDGE_DB` на существующий файл только после проверки резервной копии; проверьте права владельца и доступ к каталогу.
6. Запустите `npm test`, затем `npm start`. При старте создаются новые таблицы и устанавливается версия схемы 17.
7. Остановите сервер и выполните `npm run verify` с `JUDGE_DB`, указывающим на обновлённую базу. Повторно запустите сервер и откройте `/api/ready`.
8. Убедитесь, что старые дела, команды, голоса, релизы и журнал доступны. Создайте тестовый бренд, выполните QA и проверьте независимое согласование на тестовой кампании.
9. При неудаче **не** открывайте обновлённую базу старым бинарником 0.15.0: он намеренно откажет из-за новой версии схемы. Для отката восстановите именно сохранённую до миграции резервную копию в отдельном каталоге.

Новые бренд-правила и целевые языки **не включаются автоматически** для старых кампаний: это обеспечивает совместимость с прежними брифами. После ручного назначения новых правил кампания получает новую редакцию и требует нового согласования.

Внутренняя локальная идентификация остаётся без подтверждения email и MFA; публичный доступ не рекомендуется. Семь внешних платформ A–G не подключаются этим обновлением автоматически.
