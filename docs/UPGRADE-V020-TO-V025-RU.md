# Обновление ADVERSE JUDGE 0.20.0 → 0.25.0

**Это инструкция локального/staging-обновления; не инструкция публичного production-деплоя.**

1. Остановите старый Node.js-сервер. Сохраните базу целиком через штатную `npm run backup`, затем `npm run backup:inspect`; не копируйте работающую SQLite вручную без согласованного WAL snapshot.
2. Сделайте вторую отдельную резервную копию `data/` и сохраните внешний `JUDGE_LEDGER_SECRET` (если использовался) в безопасном менеджере секретов. Никогда не включайте другой ledger secret на существующей истории.
3. Распакуйте 0.25.0 в новую папку. Не копируйте поверх предыдущих `server/`, `public/`, `tests/` или `data/` одновременно.
4. Убедитесь, что Node.js ≥22.13. Сначала запустите `npm run check` и `npm test` без пользовательской базы. Ожидается 184 успешных теста в поставляемом тестовом наборе.
5. Перенесите корректно закрытую/экспортированную SQLite в `data/judge.sqlite` новой папки либо укажите прежний путь через `JUDGE_DB`. Сохраните прежний HMAC-секрет и настройки происхождения запросов.
6. Запустите `npm start`. Схема обновится **17 → 22**. Выполните `npm run verify`, затем проверьте реальный старый вердикт, голос, командное пространство, кампанию и подписанный выпуск.
7. Откройте «Кампании» → выбранная кампания → «Управление рисками и выпуском». Подтвердите, что критических замечаний нет. Включайте обязательное связывание источников лишь после готовности материалов и ручной проверки.
8. Проверьте `npm run integrations:audit` и `npm run ops:doctor`. **0/7 партнёров и `productionReady=false` — ожидаемый честный результат**, если сайты не подключены.
9. Для отката остановите сервер и восстановите **старую версию кода вместе с резервной копией SQLite схемы 17**. Запуск старой версии против базы схемы 22 не поддерживается.

### Что не переносится автоматически

Подключения реальных рекламных сайтов, SSO, облачный Postgres, коммерческий биллинг и статусы фактической доставки не появляются после обновления. Их нельзя восстанавливать из лабораторного mock-контракта.
