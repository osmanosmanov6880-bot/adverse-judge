# ADVERSE / JUDGE 0.3.0 — эксплуатация локального пилота

## Обновление с 0.2.0 до 0.3.0

1. Остановите старый сервер JUDGE и **сохраните всю папку `data`** в закрытом месте. Для корректного SQLite snapshot используйте штатный `npm run backup` ещё на старой версии. Не копируйте работающую БД как обычный файл без WAL.
2. Распакуйте 0.3.0 **в новую папку**. Никогда не распаковывайте поверх действующего сервера и не помещайте реальные секреты в архив исходников.
3. Скопируйте старую проверенную базу в новую `data/judge.sqlite`. Запуск `npm start` автоматически выполнит миграцию схемы 1 → 2. **Откат обратно на 0.2.0 после миграции не поддерживается.** Для отката используйте защищённую копию базы и прежнюю версию приложения.
4. Выполните `npm run verify` и `npm test`. При несовпадении событий с состояниями прекратите операции; восстановите согласованную копию.
5. Созданные ранее, но ещё не полученные signed-передачи **не погашаются**, поскольку у них нет доказуемого `verdict_id`. Выдайте новые ссылки.
6. Проверьте `npm run integrations:check`. Все семь конфигураций по умолчанию остаются `clipboard` до согласования реальных URL/API.

Для диагностики внешних подтверждений смотрите `docs/INTEGRATION-CONTRACT-RU.md`. Устойчивость подписанных ссылок и callback проверена на фиктивном получателе; это не проверка реальных сайтов.

## Проверка перед началом

```bash
node --version                   # требуется >=22.13.0; тестировалось на 22.16.0
npm run check
npm test
npm run demo                    # обновляет dist/JUDGE-ADVERSE-preview.html
npm start                       # HTTP://localhost:3000
```

Node использует экспериментальный `node:sqlite`. У пилота **нет** production SLA и защиты от компрометации системного администратора. Требуется отдельное ответственное тестирование перед публикацией.

## Обновление с 0.1.0

1. Закройте старый процесс JUDGE штатным `Ctrl+C` или SIGTERM, а не принудительным завершением всех процессов.
2. Скопируйте **после остановки** всю папку `data` старого JUDGE во временное закрытое расположение, не прикрепляйте её к публичным тикетам.
3. Распакуйте v0.2.0 в отдельный каталог.
4. Поместите проверенную базу в `data/judge.sqlite` нового каталога; не помещайте её внутрь `public` или `dist`.
5. `npm run verify`, затем `npm run backup` и сохраните созданную копию в защищённом от чужого доступа хранилище.
6. `npm start`, войдите в прежний аккаунт/гостевую сессию и откройте существующее дело. Новые события `owner_reopen` сохраняют совместимость со старой структурой SQLite (`user_version=1`).

**Внимание:** у гостевых сессий нет восстановления без старого cookie. Если browser cookies потеряны, перенос файла не даёт доступа к гостевым делам. Не удаляйте старый каталог до проверки.

## Целостность и резервы

```bash
npm run verify                         # read-only проверка active SQLite
npm run backup                         # безопасная snapshot-копия в backups/
node scripts/verify-db.mjs /path/backup.sqlite
```

`verify` проверяет `PRAGMA integrity_check`, внешние ключи и воссоздание всех состояний из событий. Результат `{ok:true}` означает только отсутствие обнаруженных нарушений этих проверок; он **не доказывает** отсутствие злонамеренной согласованной подмены БД.

`backup` пишет `backups/JUDGE-<timestamp>.sqlite` и `<file>.json` с размером, SHA-256 и результатами проверки. Копия содержит email, пароли в виде хешей, рекламные материалы и все события **без шифрования**. Не храните её в Git, публичном bucket или переписке; шифруйте вне приложения, установите права доступа и сроки хранения. Внутренние резервные копии могут сохранять удалённые персональные данные до конца установленного срока.

Для восстановления: остановите сервер, проверьте резервную копию скриптом и её SHA-256 по sidecar, сохраните старый DB в защищённом расположении, скопируйте SQLite из snapshot в новый `data/judge.sqlite`, затем `npm run verify` и перезапустите JUDGE. Не подменяйте живую SQLite обычным копированием файла на работающем сервере.

## Защита данных и права

На уровне кода есть per-owner изоляция, HttpOnly/SameSite cookie, CSRF и проверка Origin/Host, лимиты входа/регистрации/ИИ, role-bound генерация и минимальный экспорт. Но локальные аккаунты не подтверждают владение email, нет сброса пароля, MFA или SSO. Поэтому **не публикуйте этот пилот как готовую систему для реальных клиентских секретов**.

Для доступного в интернете сервиса нужны: TLS у обратного прокси, фиксированный `APP_ORIGIN=https://...`, секреты вне репозитория, производственная система пользователей, отладка лимитов с несколькими экземплярами, аудит зависимостей/инфраструктуры, DPA с провайдерами, политика retention/удаления backup, логирование ошибок без копирования содержимого дел, платежная и юридическая проверка.

## Аналитика и критерии выпуска

`/analytics` показывает только события текущего владельца, не глобальные метрики посетителей. Строки `handoff_created`, `handoff_redeemed`, `useful_action` различаются. Нельзя считать копирование брифа подтверждением, что платформа создала объявление. Для измерения регистрации, переходов между семью сайтами и оплат нужны их настоящие API, cookie/consent стратегия и отдельное согласование событий.

## Статус внешних систем

- Все платформы A–G **не настроены**, пока не предоставлены реальные URL и контракты.
- Внешняя LLM опциональна и выключена по умолчанию; тесты используют фейковый Responses API, платных вызовов не было.
- В GitHub, Supabase, Stripe и на живом сервере этот релиз **не опубликован**.
- Рассмотрение дела в JUDGE — редакторская помощь, а не юридическая или рекламная экспертиза.
